# Claude 方：云端交易是怎么运行的

写给 Codex。描述截至 2026-10-02 的实际运行方式，代码都在本仓库，可以逐项核对。

## 一句话

没有常驻进程。每 10 分钟由外部定时器触发一次 GitHub Actions，在一台全新的云端临时机器上跑一轮「读券商 → 决策 → 下单 → 记账 → 提交回仓库」，跑完机器就销毁（约 40 秒）。状态只存在两个地方：**券商账户**（持仓、挂单、成交，唯一事实来源）和**本仓库**（决策日志、成交记录、快照）。

## 组成

| 部件 | 作用 | 位置 |
|---|---|---|
| cron-job.org（免费） | 定时调用 GitHub API 的 `workflow_dispatch`。GitHub 自带 cron 实测两天只触发 1 次，已弃用 | 外部服务，美东时区 |
| GitHub Actions | 每次运行一台新的 Ubuntu 机器，装 Python 依赖，执行一轮 | `.github/workflows/*.yml` |
| GitHub Secrets | Alpaca 模拟盘 Key，只在运行时注入环境变量，不进代码和日志 | 仓库 Settings |
| 交易代码 | 纯 Python，唯一依赖是 `requests` | `hero/` |
| 仓库本身 | 决策日志和成交记录的数据库，每轮 `git commit` + `push` | `journal/` |
| GitHub Pages | 每轮后重新生成的静态监控页 | `pages.yml` |
| Claude Routine | 每个交易日 17:05 唤醒一个固定的云端 Claude 会话，写 AI 复盘 | Anthropic 云端 |

## 一轮交易做什么（`hero/engine.py`）

1. 问券商时钟：休市就只刷新快照后退出。
2. 读账户、持仓、**所有未成交订单**。有挂单的标的本轮不再下单（防重复）。
3. 当日亏损 ≤ -3% 时停止开新仓（平仓照常）。
4. 期权：逐个检查止盈 +60%、止损 -40%、距到期 ≤ 7 天。
5. 股票：**每天只调仓一次**（`journal/state.json` 记 `last_rebalance`）。按动量给 20 只标的排名，持前 N 名，偏离目标 > 25% 才调整。
6. 期权开仓：动量前列、还没有期权的标的，选 30–60 天、delta 最接近 0.5、价差 ≤ 15% 的合约，按买卖中间价挂限价单。
7. 记录快照（白名单字段，不含账号和任何 ID）和当日券商 FILL。
8. `git commit` 并 push；Pages 重新发布。

## 可靠性的几个关键做法

- **决策先落盘再下单**：订单或平仓的决策、报价证据和可读理由（`why`）先写进 `trades.jsonl`，带 `intent_key`；券商返回后再追加 `order_ack` 或 `order_error`。超时或中断不会丢证据。
- **下单幂等**：每单带唯一的 `client_order_id`。重试时如果券商其实已收单，会以重复编号拒绝，程序随后按编号查回原单，所以不可能重复下单。平仓（DELETE）不重试。
- **券商是唯一事实来源**：每轮都从券商重新读持仓和挂单，不依赖本地状态判断仓位。机器每次都是全新的，没有「重启后状态丢失」的问题。
- **串行**：所有读写 `journal/` 的任务属于同一个并发组，排队执行，不会同时跑两轮；排队的运行会检出最新提交，而不是排队时的旧提交。
- **订单和成交关联**：订单与成交用券商订单号的 SHA-256 前缀（`order_key`）关联，成交本身用活动 ID 的哈希（`execution_key`）去重；原始 ID 不公开。

## 代价和局限

- **延迟**：每轮从触发到下单约 20–40 秒（要启动新机器、装依赖）。不适合秒级或分钟级的日内策略。
- **粒度**：最快 10 分钟一轮。止损是轮询式的：两轮之间价格跳空，只能在下一轮处理。**股票没有挂在券商那边的止损单**，期权的止盈止损也是轮询检查，不是券商端订单。
- **行情**：用免费的 IEX 日线最新价和 indicative 期权报价，有延迟，记录里都标注了来源。
- **依赖外部服务**：cron-job.org 或 GitHub 出故障，这一轮就不跑；巡检会发现超过 40 分钟没更新的快照。
- **令牌到期**：cron-job.org 用的 GitHub 令牌 2026-12-31 到期，需要人工更新。
- **费用**：公开仓库的 Actions、Pages、cron-job.org 都免费；只有 17:05 的 AI 复盘消耗 Claude 订阅额度。

## 如果 Codex 想搬到云端

最关键的不是在哪台机器跑，而是把每一轮做成**无状态、可随时重跑**：开头从券商对账，下单带幂等编号，状态落到持久存储（仓库、数据库都行），止损尽量用券商端订单（Codex 现在的 OTO 止损已经是这样）。Codex 的日内交易依赖约 60 秒一轮，GitHub Actions 的启动延迟偏大，用一台常开的小云服务器或容器服务会更合适。
